# Contributing

Thanks for wanting to help. Bug reports, term proposals, feature ideas, and pull
requests are all welcome.

## Which way in

The vocabulary and the repository take contributions differently, because they
are maintained differently.

**The vocabulary is authored in the [Intentional Arrangement SKOS Editor](https://github.com/jesstalisman-ia/intentional-arrangement-skos), 
which was developed by Jessica Talisman**, exported to `vocab/src/pkm-vocab.export.ttl`, and built
from there. Everything under `vocab/`, `agents/`, and `resources/` — the bulk
dump, all 241 per-term files, the index pages — is generated by `make build`. A
pull request editing those files can't be merged, because the next build
overwrites it. So vocabulary changes come in as issues and I make them in the
editor:

- **New concept** → [propose a term](https://github.com/dpw67/pkm/issues/new?template=term_proposal.yml)
- **Change an existing concept** → [propose a change](https://github.com/dpw67/pkm/issues/new?template=term_change.yml)

**Everything else takes pull requests** — `docs/`, `examples/`, `scripts/`,
`generators/`, `schema/`, `shapes/`, and the hand-authored Turtle (`void.ttl`,
`ontology/pkm.ttl`, `taxonomy/pkm-taxonomy.ttl`).

For anything security-related, follow [SECURITY.md](SECURITY.md) instead of
opening a public issue.

## Report a bug or request a feature

- **Bug** → [bug report](https://github.com/dpw67/pkm/issues/new?template=bug_report.yml)
- **Feature** → [feature request](https://github.com/dpw67/pkm/issues/new?template=feature_request.yml)
- Browse [open issues](https://github.com/dpw67/pkm/issues) first; a 👍 on one that matches yours helps it rise.

## What a term needs

Conventions the vocabulary already follows, so a proposal that meets them is
quick to accept:

- **A definition and a scope note, both.** All 223 concepts have both today. The
  definition says what the thing is; the scope note says when to use it and when
  to reach for a neighbour instead. The scope note is what keeps two similar
  terms apart, so it does more work than it looks like it does.
- **A natural-language preferred label.** `Day Meal Plan`, not `DayMealPlan` and
  not `day_meal_plan`. `rdfs:label` mirrors it automatically.
- **A parent, in an is-a-kind-of relationship.** `skos:broader` is for genuine
  specialisation. Part-of and merely-associated both belong in `skos:related`.

## URI policy

- **URIs are minted from the preferred label once, at creation**, and do not
  follow later label changes. Correcting `Day.Meal Plan` to `Day Meal Plan` in
  0.1.4 left `pkmv:DayMealPlan` exactly as it was.
- **A published URI is never removed or reused.** All 241 URIs from 0.1.1 still
  mean what they meant, and still dereference — Turtle for an RDF client, an
  HTML page for a browser, from the same URI.
- **Retirement is deprecation, not deletion** — `owl:deprecated true` plus
  `dcterms:isReplacedBy` where there's a successor. `make build` reports orphaned
  term files rather than deleting them, so this is enforced by the build.

See [CHANGELOG.md](CHANGELOG.md) for the versioning levels and what counts as a
breaking change.

## Pull requests

1. Fork the highest-numbered `0.x.y` branch — never `main`.
2. Keep the change focused: one feature or fix per PR.
3. Update anything in `docs/` your change affects.
4. Open the PR against that same version branch, with a short description of what and why.

Two things worth knowing before you start:

- **`main` is live.** Merging to `main` publishes the namespace at w3id.org/pkm
  immediately, with no staging step. That's why PRs target a version branch.
- **Don't edit generated files.** If your diff touches `vocab/`, `agents/`, or
  `resources/`, it will be overwritten — the change belongs in an issue instead.

Maintainers run `make check`, `make validate`, and `make artifacts` before
merging vocabulary source changes.

## Standards to keep in mind

This project is built on standards. Changes should be consistent with this
vocabulary and with **W3C SKOS**, **ANSI/NISO Z39.19**, **ISO 25964**, and
**DCMI**, where relevant. When in doubt, cite the spec in the PR or issue.
